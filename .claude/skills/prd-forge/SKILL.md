# PRD Forge

把模糊的业务需求，锻造成研发能照着做、测试能照着验、验收时能拿着对账的产品需求文档。

## 核心立场

这四条是本 Skill 的判断依据，与用户的偏好冲突时以此为准并说明原因：

1. **PRD 是契约，不是方案。** 只写「系统在什么条件下必须表现出什么行为、如何判定通过」。不写技术选型、不写表结构、不写接口实现。写进技术方案的内容会随实现变化而失效，写进契约的内容才是验收依据。
2. **不可验证的需求等于没有需求。** 每条功能需求必须能被一个测试用例判定真假。无法判定的表述（"体验流畅""性能优良"）一律降级为待澄清项，不允许进入正式需求条目。
3. **不替业务方做决定。** 关键业务规则缺失时必须提问。允许给兜底假设让流程继续，但假设必须显式标注在文档的「开放问题」中，且不得伪装成已确认的需求。
4. **文档重量匹配需求重量。** 改一句文案不需要八章 PRD。过度文档化与文档缺失同样是交付缺陷。

## 工作流程

按 Step 0 → 4 顺序执行。用户明确只要某一阶段产物时，直接跳到该阶段。

### Step 0 · 定级

先判断需求该产出什么，再决定投入多少。分级规则见下表，拿不准时向上一级靠。

| 级别 | 判定条件 | 产出物 | 章节范围 |
|---|---|---|---|
| **L0 微变更** | 文案、样式、单个字段增删；不影响流程与数据模型 | 变更说明（3 行：改什么 / 为什么 / 怎么验收） | 不写 PRD |
| **L1 轻量** | 单页面、单功能点调整；影响局部流程 | 1–2 页 | 第 1、3、8 章 |
| **L2 标准** | 新增功能模块；涉及新流程、新数据、跨角色 | 标准 PRD | 第 1–8 章（第 4 章状态机按需） |
| **L3 完整** | 新业务线、跨系统集成、涉及资金/权限/合规 | 标准 PRD + 评审包 | 第 0–8 章全量 + 追踪矩阵 + 评审记录 |

判定为 L0 时，直接输出变更说明并结束，不要继续走后续流程。判定为 L3 时，在 Step 3 之后追加一次独立的对抗式评审（见 Step 4 的 L3 分支）。

### Step 1 · 澄清（不可跳过）

在动笔前完成需求澄清。目标是拿到「目标 / 角色 / 范围 / 规则 / 验收」五要素，而不是拿到一份完整需求。

执行要求：

- **最多提 5 个问题**，按「阻塞程度」排序——只问那些答案不同会导致 PRD 结构不同的。次要疑问写进「开放问题」章节，不占用提问额度。
- 每个问题**必须附带兜底假设**，格式为「若不回答，我按 X 推进」。用户不答也能继续。
- 提问前先检索用户已提供的信息（对话、附件、代码库、历史文档），不要问已经答过的事。
- 问题清单与业务域分类模板见 `references/question-playbook.md`，按业务域取用，不要一次问完。

识别出的模糊点分三类处理：

| 类型 | 处理方式 |
|---|---|
| 缺事实（不知道现状如何） | 提问，或标注为待调研 |
| 缺决策（有多个合理选项） | 提问并列出选项与影响，不替业务选 |
| 缺细节（不影响结构与验收） | 写进开放问题，按行业常规给默认值并标注 |

### Step 2 · 撰写

以 `assets/prd-template.md` 为骨架产出文档。写每一章前，先查 `references/section-guide.md` 中该章的质量标准与常见错误。

撰写时必须遵守的硬规则（细则见 `references/quality-rules.md`）：

1. **功能需求编号**：`FR-001` 起连续编号，同一文档内唯一，永不复用已废弃编号。非功能需求用 `NFR-xxx`，用户故事用 `US-xxx`。
2. **一条需求一个行为**：一个 FR 只描述一个可独立验收的系统行为。出现「并且」「同时支持」时，拆成两条。
3. **描述主语是系统**，不是用户。写「系统必须在 X 条件下执行 Y」，不写「用户可以 Y」。
4. **每条 FR 必须包含**：优先级、关联目标、描述、业务规则、异常与边界、验收标准。缺任一项即为不合格需求。
5. **验收标准用 Given / When / Then**，且 Then 部分必须是可观测、可断言的结果（返回值、状态变化、界面元素、日志、数据落库），不能是主观感受。
6. **非功能需求必须带数值**：响应时间写毫秒、并发写 QPS、可用性写百分比、容量写条数。写不出数值的，标注为「待压测确定」并列入开放问题。
7. **明确非目标**：写出本次不做的事及排除原因。非目标章节缺失是范围蔓延的首要原因。
8. **优先级用 P0/P1/P2/P3**，并在文档开头定义每一级的判定标准，避免全员 P0。

生成骨架时优先使用脚本，而不是手抄模板：

```bash
python scripts/init_prd.py --title "需求名称" --level L2 --out prd.md
```

### Step 3 · 自检门禁

交付前必须执行确定性检查，不能靠"我读了一遍觉得没问题"：

```bash
python scripts/prd_lint.py prd.md
```

脚本输出 ERROR / WARN 两级问题清单与评分。处理规则：

- **ERROR 必须全部清零**才能交付。ERROR 表示文档存在结构性缺陷（缺章节、需求无验收标准、编号重复、占位符残留）。
- **WARN 逐条判断**：能改则改；确认是误报或业务上确实如此的，在回复中说明理由，不要静默忽略。
- 退出码非 0 时不要声称文档已完成。
- 用户要为团队设 CI 卡点时，加 `--strict`（WARN 也阻断）。不要用默认模式做卡点——默认模式不拦 WARN，而 NFR 未量化、追踪矩阵漏需求恰好都在 WARN 里。
- 团队内部术语被误判为模糊词时，用 `--allow "术语1,术语2"` 豁免，并把该术语记进团队的检查约定，不要每次口头解释。

脚本查不出的部分（需求是否真的解决了业务问题、规则之间是否自相矛盾、边界是否覆盖完整）必须人工复核，核对 `references/section-guide.md` 末尾的交付核对清单。

### Step 4 · 交付

输出内容包含三部分：

1. **PRD 正文**（Markdown 文件），文件名格式 `<需求名>-PRD-v<版本>.md`。
2. **lint 结果摘要**：评分、ERROR/WARN 数量、未修复项的处置说明。
3. **待确认清单**：所有假设、开放问题、待调研项，合并成一张表，标明负责人与阻塞程度。

**L3 分支**：追加一轮对抗式评审。以「独立评审人」身份重新通读文档，专门找四类问题：需求之间互相冲突、异常路径未覆盖、权限与数据隔离有漏洞、验收标准无法证伪。评审结论单独成节，不要合并进正文修改记录。

## 边界

- 不产出技术方案、数据库设计、接口定义。这些属于技术设计文档，PRD 中出现即为越界，改为在该需求下注明「实现方式待技术方案确定」。
- 不替用户拍板商业决策（定价、优先级取舍、合规口径）。给出选项与影响分析，由业务方决策。
- 不评估排期与人力。可以标注依赖关系与工作量相对大小，不给日期承诺。
- 不承诺文档能消除所有歧义。只能保证：歧义被显式标注，而不是被隐藏。
