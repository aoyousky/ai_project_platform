# 需求质量规则

判断一条需求是否合格，不靠感觉，靠下面这组可执行的检查项。

## 一、可验证性三问

每条需求过三关，任一关不过即为不合格：

1. **能构造出反例吗？** 假设研发做了另一个实现，你能用一个具体场景证明它做错了？
2. **测试能写出用例吗？** 给定前置条件，执行操作，断言结果——三步能写全？
3. **上线后能判定通过吗？** 不依赖"看起来还行"这类主观判断？

三问全过，才允许写进需求条目。有一问卡住，说明这条需求还是意图而非需求，退回澄清。

## 二、验收标准：Given / When / Then

### 结构

```
Given <前置状态：数据、角色、环境>
When  <触发动作：用户操作、系统事件、时间到达>
Then  <可观测结果：返回值、状态变更、界面元素、落库数据、日志、通知>
```

### Then 必须落在可观测的载体上

| 可观测载体 | 示例 |
|---|---|
| 接口返回 | 返回 HTTP 200，body 中 `sessionId` 为非空 UUID |
| 数据状态 | 数据库 `order.status` 由 `PENDING` 变为 `PAID` |
| 界面元素 | 页面顶部出现 toast「保存成功」，3 秒后自动消失 |
| 列表内容 | 列表仅展示当前租户数据，条数为 3 |
| 外部副作用 | 向用户手机号发送一条含 6 位验证码的短信，5 分钟内有效 |
| 日志与监控 | 记录一条 level=WARN 的日志，字段 `reason=quota_exceeded` |

### 一条需求的验收标准数量

- 至少 1 条正向（主流程走通）
- 至少 1 条异常（非法输入 / 越权 / 超限 / 并发）
- 业务规则每多一条，验收标准至少多一条

只有正向用例的需求不算合格——异常路径才是线上事故的高发区。

## 三、模糊词黑名单

出现下列词，且所在句子没有数值或明确参照，一律标记为不可验证：

| 模糊词 | 问题 | 替换方向 |
|---|---|---|
| 快速 / 迅速 / 及时 | 无时间边界 | 写具体时限：≤ 300 ms / 5 秒内 / T+1 日 |
| 友好 / 易用 / 流畅 | 无判定标准 | 写可测代理指标：任务完成步数 ≤ 3 步、首次成功率 ≥ 90% |
| 高效 / 优化 / 提升 | 未定义基准与幅度 | 写「从 X 降到 Y」，附基线来源 |
| 尽量 / 尽可能 | 无强制力 | 改为明确的降级策略与优先级 |
| 合理 / 适当 / 合适 | 判断标准在作者脑中 | 写判定规则或交由业务方决策 |
| 大幅 / 显著 / 明显 | 无法度量 | 写具体百分比或绝对值 |
| 若干 / 多个 / 等 | 数量不明 | 写上限或枚举 |
| 支持多种 / 兼容主流 | 范围无边界 | 枚举清单或写引用标准 |
| 简单 / 便捷 | 主观 | 写操作步数、必填字段数 |
| 完善 / 健全 | 无验收终点 | 拆成可枚举的具体条目 |

**例外**：出现在「背景」「开放问题」章节时不算错误——那里本来就是描述不确定性的地方。规则只约束需求正文与验收标准。

## 四、需求原子性

一个 FR 只能包含一个可独立验收的行为。检测信号：

| 信号 | 处理 |
|---|---|
| 句子含「并且」「同时」「以及」连接两个动作 | 拆成两条 FR |
| 一条 FR 的验收标准超过 5 条 | 通常说明粒度太粗，考虑拆分 |
| 一条 FR 涉及两个不同角色 | 大概率应拆成两条（权限与流程往往不同） |
| 一条 FR 的异常表超过 6 行 | 可能是多个功能的异常混在一起 |

拆分后每条独立编号，不要用 FR-001a / FR-001b——这类编号在追踪矩阵中容易丢失。

## 五、非功能需求量化对照表

| 类别 | 不可接受写法 | 可接受写法 |
|---|---|---|
| 性能 | 响应要快 | P95 ≤ 300 ms（100 QPS 下） |
| 性能 | 支持高并发 | 峰值 5000 QPS 时错误率 < 0.1% |
| 容量 | 数据量很大 | 单租户 100 万条，单条 ≤ 2 KB |
| 可用性 | 高可用 | 月度可用性 ≥ 99.9%，RTO ≤ 30 min，RPO ≤ 5 min |
| 安全 | 保证安全 | 敏感字段 AES-256 加密存储，传输 TLS 1.2+，越权访问返回 403 |
| 兼容性 | 兼容主流浏览器 | Chrome ≥ 100、Safari ≥ 15、Edge ≥ 100 |
| 可维护性 | 代码规范 | 单元测试覆盖率 ≥ 70%，关键路径 100% |
| 国际化 | 支持多语言 | 首发 zh-CN、en-US；文案与代码分离；时区按用户设置 |

写不出数值时的正确处理：写「待压测确定」，并在第 7 章开放问题中登记负责人与确认时间。**不允许留空**，也不允许用形容词占位。

## 六、优先级判定

先定义再使用。文档开头必须写明各级判定标准，否则会出现「人人都是 P0」。

| 级别 | 判定标准 | 占比参考 |
|---|---|---|
| P0 | 不实现则本版本无法上线（合规、资金安全、主流程断点） | ≤ 30% |
| P1 | 影响核心体验或核心指标，本期必须交付 | ≤ 40% |
| P2 | 有增益但可延后，不影响本次验收 | 其余 |
| P3 | 已识别但明确不做，记录备查 | — |

P0 占比超过 40% 时，说明优先级没有真正做取舍，需回到 Step 1 与业务方重新对齐。

## 七、需求粒度的经验边界

| 粒度 | 特征 | 是否合适 |
|---|---|---|
| 太粗 | 「实现订单管理」 | 否——无法独立验收，需拆到行为级 |
| 合适 | 「创建订单时校验库存不足则拒绝并返回缺货明细」 | 是 |
| 太细 | 「订单号第 3 位为校验位」 | 否——属于实现细节，写进业务规则而非独立 FR |

判断标准：**能不能被一个测试用例独立验收**。能，就是合适粒度。

## 八、常见句式模板

直接套用，减少每次重新组织语言的成本：

```
系统必须在 <条件> 时 <行为>，否则 <替代行为>。
系统不得在 <条件> 下 <禁止行为>。
当 <异常> 发生时，系统必须 <兜底行为>，并向用户展示 <反馈文案要点>。
<字段> 的取值必须满足 <约束>，违反时返回 <错误码> 与 <提示>。
同一 <实体> 在 <时间窗口> 内最多允许 <次数> 次 <操作>，超出后 <处理>。
```

## 九、写完后自问的五个问题

1. 这份文档交给一个没参加过需求会的研发，他能直接开工吗？
2. 交给测试，他能写出用例而不来问「这里到底要怎样」吗？
3. 上线后出现争议，双方能指着某一节判定谁对谁错吗？
4. 有没有哪条需求，实现的自由度大到可以做出两种完全不同的产品？
5. 所有「我觉得应该」的地方，是不是都变成了「文档里写着」？
