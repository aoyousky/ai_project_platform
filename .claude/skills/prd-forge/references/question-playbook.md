# 澄清提问手册

PRD 质量的 80% 决定于动笔前问对了什么。这份手册解决一个具体问题：**在最多 5 个问题的额度内，问出最有价值的那几个。**

## 一、提问前必做的三件事

1. **先自查已有信息**：对话历史、上传的附件、会议纪要、代码库、历史 PRD。已经说过的不要再问，问了会显得没读材料。
2. **判断问题类型**：缺事实（去查）／缺决策（必须问人）／缺细节（给默认值）。只有「缺决策」值得占用提问额度。
3. **准备兜底假设**：每个问题都带「若不回答，我按 X 推进」。这样用户不答也能交付，而不是卡住。

## 二、问题排序原则

按「答案不同会导致 PRD 结构不同」的程度排序：

| 优先级 | 问题类型 | 为什么排前面 |
|---|---|---|
| 1 | 范围边界（做不做某块） | 决定章节数量与需求条数 |
| 2 | 角色与权限模型 | 决定权限矩阵与异常路径 |
| 3 | 核心业务规则与判定条件 | 决定 FR 数量与状态机复杂度 |
| 4 | 异常与失败处理策略 | 决定异常表内容 |
| 5 | 成功指标与观测方式 | 决定埋点章节 |

**不要问的**：文案措辞、UI 细节、技术选型、排期。这些要么不影响结构，要么不该由产品经理定。

## 三、通用五要素问题（默认起点）

没有特定业务域信息时，用这五个：

1. 这次要解决的具体问题是什么？有没有数据或案例能说明它的规模？
2. 涉及哪些角色？每个角色能做什么、不能做什么？
3. 本期明确不做什么？（这条比"做什么"更能界定范围）
4. 有没有必须遵守的业务规则或合规要求？（比如金额上限、审批层级、数据保留期限）
5. 上线后用什么指标判断这件事做成了？现在这个指标是多少？

## 四、按业务域问题库

按需求所属域取用，每个域取 2–3 个，不要全问。

### 交易 / 支付 / 订单

- 订单状态有哪些？每个状态能否回退？退款、部分退款、超时关闭分别走哪条路径？
- 金额计算在哪里做？优惠、税费、运费的计算顺序是什么？出现分位差（如 0.01 元）如何归属？
- 幂等要求：用户重复提交、网络重试、回调重复通知，系统如何保证不重复扣款/不重复发货？
- 对账口径：以支付渠道流水为准还是以本地订单为准？差异如何处理？

### 账号 / 权限 / 多租户

- 租户之间是否允许共享数据？共享的范围与授权方式是什么？
- 角色是固定的几种，还是允许自定义？权限粒度到菜单、按钮还是数据行？
- 用户离职、角色变更、租户注销时，其历史数据如何处理？
- 是否存在越权访问的已知场景？（跨租户、越级审批、代操作）

### 内容 / 社区 / UGC

- 内容审核是机审、人审还是组合？审核中、审核驳回的内容对作者和读者分别可见什么？
- 举报与申诉的流程与时效要求？
- 删除是软删还是硬删？删除后是否影响已产生的统计数据？
- 敏感词与违规内容的判定标准由谁维护、多久更新？

### 数据报表 / 看板

- 指标口径由谁定义？与现有报表口径是否一致？不一致时以谁为准？
- 数据延迟容忍度是多少？（实时 / 准实时 / T+1）
- 数据权限：谁能看全量，谁只能看自己范围？导出是否也受同样限制？
- 历史数据回溯：口径变更后是否需要重算历史？重算窗口多长？

### 消息 / 通知 / 触达

- 触达渠道有哪些？同一事件多渠道时的优先级与去重规则？
- 用户退订、免打扰时段、频次上限如何处理？
- 发送失败的重试策略与最终失败后的兜底（站内信？人工？）
- 模板内容由谁维护？是否需要多语言？

### B 端后台 / 运营工具

- 操作是否需要审批？审批层级与驳回后的状态如何流转？
- 批量操作的上限是多少？部分失败时是全部回滚还是部分成功？
- 操作是否需要留痕审计？审计日志保留多久、谁能查？
- 高危操作（删除、导出全量、改配置）是否需要二次确认或双人复核？

### AI / 智能功能

- 输出的准确率期望是多少？错误输出的可接受比例与兜底方式？
- 用户是否知道自己在与 AI 交互？是否需要显式标注？
- 输入内容是否包含个人信息或商业机密？是否可以送出到第三方模型？
- 生成失败、超时、内容被安全策略拦截时，用户看到什么？
- 是否需要人工反馈入口？反馈数据如何回流？

### 系统集成 / 第三方对接

- 对接方的接口能力与限制（QPS、超时、重试策略）是否已确认？
- 对方不可用时，本系统是降级、排队还是直接报错？
- 数据同步是推还是拉？失败补偿机制是什么？
- 双方字段含义是否一致？不一致时以谁为准、在哪一层做转换？

## 五、提问话术模板

提问要带上下文和兜底，让用户回答成本最低。

**单个问题**
```
关于 <主题>，需要确认一点：<具体问题>？
- 如果选 A，我会 <对应写法>
- 如果选 B，我会 <对应写法>
- 如果不方便确认，我先按 A 写，并登记为开放问题 Q-001
```

**批量提问（5 个以内）**
```
动笔前需要确认 5 个会影响文档结构的问题。每个问题我都附了默认处理方式，
你只回复不同意的部分即可，其余我按默认推进。

1. <问题> ｜ 默认：<假设>
2. <问题> ｜ 默认：<假设>
...
```

**追问（用户回答模糊时）**
```
你提到「<用户原话>」，这个表述我可以有两种理解：
- 理解一：<具体化>，对应需求写为 <示例>
- 理解二：<具体化>，对应需求写为 <示例>
哪种更接近你的意思？这会影响 <具体影响>。
```

## 六、什么时候停止提问

满足以下任一条件即可动笔：

- 五要素齐了（目标、角色、范围、规则、验收）
- 剩下的疑问都不影响需求结构，只是措辞细节
- 用户明确表示「你先按你的理解写」

停止提问后，把未解决的疑问全部登记进第 7 章开放问题表，**不要带进正文冒充已确认内容**。

## 七、反面示例

| 不好的提问 | 问题所在 | 改法 |
|---|---|---|
| 「你有什么需求？」 | 太开放，用户要重新讲一遍 | 基于已有信息提具体问题 |
| 「要做得好看吗？」 | 不影响结构，浪费额度 | 不问，UI 交给设计 |
| 「用 MySQL 还是 PG？」 | 技术选型不是产品经理的事 | 不问，写「实现方式待技术方案确定」 |
| 「优先级是什么？」 | 太笼统，用户答不出 | 「如果只能先做三块，你砍哪两块？」 |
| 「还有别的吗？」 | 无边界，用户会漏 | 按业务域清单逐项确认 |
