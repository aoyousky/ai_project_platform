# 质量检验方法

回答一个问题：**怎么判断一份 PRD 是不是真的合格，以及怎么判断检验本身有没有失效。**

分四层，从便宜到贵，前三层验文档，第四层验检验本身。

---

## 第一层 · 机器门禁（必做，可复现）

```bash
python scripts/prd_lint.py <文件> --level L2
python scripts/prd_lint.py <文件> --level L2 --strict      # CI 卡点用
python scripts/prd_lint.py <文件> --allow "内部术语,另一个术语"
```

- 退出码 0 表示无 ERROR，1 表示有 ERROR，2 表示参数或文件错误。
- `--strict` 下 WARN 也判定为未通过（退出码 1），用于 CI 卡点。默认模式不阻断 WARN，因为 WARN 里有误报，硬卡会让团队绕过流程。
- `--allow` 用于豁免团队内部术语，避免被模糊词表误伤（如「提升额度」「查询优化器」已内置豁免）。
- `--json` 输出便于二次处理。

**这一层能证明什么**：结构性缺陷不存在（缺章节、需求无验收标准、编号重复、占位符残留、非功能需求未量化、追踪矩阵遗漏）。

**这一层不能证明什么**：需求内容是否正确、规则之间是否冲突、验收标准是否覆盖了真实业务场景。评分 100 只代表"形式上可以交付"，不代表"需求做对了"。

**格式兼容范围**：章标题 `## 3. 功能需求` 与 `## 3 功能需求` 均可；需求标题 `###` 到 `######` 均可；验收标准接受 `- [ ]`、`-`、`1.` 三种写法。超出这个范围的写法会触发 W114（疑似需求标题未被识别），不会静默跳过。

---

## 第二层 · 结构核对（必做，人工）

脚本只能查它被写死的规则。下列内容需要人对照：

1. `references/section-guide.md` 末尾的 16 项交付核对清单，逐条打勾。
2. `references/anti-patterns.md` 的 14 条反模式，逐条比对。
3. 五分钟快速扫描：看非目标章节是否存在、随机抽 3 条需求看 Then 是否主观、搜「等/尽量/适当/合理」、看异常表行数、看追踪矩阵测试用例列、看 P0 占比。

**最容易被跳过的一项**：异常表行数。只有一两行的异常表，几乎必然遗漏了并发、超时或状态非法。

---

## 第三层 · 反向可用性测试（金标准，需要第二个人）

前两层都是"作者视角"。真正决定质量的，是**没参与需求会的人能不能据此干活**。

做法：把 PRD 交给一位未参加澄清与撰写的研发和一位测试，请他们各自回答：

1. 你要先建哪几张表？哪些字段你没把握？
2. 你会把这个需求拆成几个任务？拆不下去的地方在哪？
3. 你能为每条需求写出一条用例吗？哪条写不出？
4. 有哪些地方你必须回来问人？请把问题原样列出来。
5. 如果上线后用户投诉"和说好的不一样"，你会引哪一节来判定？

**判读标准**：他们提出的问题数量，就是这份 PRD 的缺陷数量。问题为 0 说明文档合格；出现"这里到底要怎样"类问题，说明该处是意图而非需求，退回补充。

这一层无法由作者自己完成——作者会用自己的隐含知识补全空白，看不出问题。这一点必须承认，不能假装。

---

## 第四层 · 变异测试（验证门禁本身是否失效）

脚本会退化。规则写错、正则写宽、字段取错，都可能让门禁变成"永远通过"的装饰品。

已经把这层做成可重复执行的评测集，改完规则直接跑：

```bash
python eval/prd_forge_eval.py          # 完整报告
python eval/prd_forge_eval.py --quiet  # 仅指标
```

评测集以一份合格 PRD 为基准做定点变异，26 个用例分四类：

| 类型 | 含义 | 判据 |
|---|---|---|
| positive | 合格文档的不同写法 | 不得报出任何问题（含 WARN） |
| planted | 植入规则集内的缺陷 | 必须命中指定错误码并拦截 |
| gap | 真实写法差异与规则盲区 | 记录，用于观察覆盖不足 |
| semantic | 结构完美但语义自相矛盾 | 记录，用于标定能力边界 |

变异带锚点断言：替换目标不存在会直接报"测试无效"，避免出现"改了但没改到"的假测试。

### 当前基线（v1.1.0）

| 指标 | 结果 |
|---|---|
| 合格文档不被误判 | 5/5，**误报率 0%** |
| 规则集内缺陷检出 | **15/15，其中 10/10 触发 ERROR 拦截** |
| 规则集外缺口检出 | 2/5 |
| 语义缺陷检出 | **0/2** |

**这两行才是关键**：规则集内全中只说明"写死的规则能用"，语义 0/2 说明**门禁对内容自相矛盾完全无感**。任何"100 分"的结论都必须叠加上第二层与第三层。

### 历史修掉的规则缺陷

| 缺陷 | 症状 | 根因 |
|---|---|---|
| W107 误判已量化 | 「P95 响应时间 \| 要足够快」通过 | 指标名与目标值拼在一起判断，P95 里的 95 被当数字 |
| E006 误伤合格文档 | 验收标准写 `1. Given` 直接 ERROR | 只认 `- [ ]` 复选框 |
| E001 误伤合格文档 | `## 3 功能需求` 缺句点被判为缺章 | 章标题正则强制要求句点 |
| 需求被静默跳过 | `#### FR-001` 的缺陷查不出 | FR 正则只认三级标题，形成绕过口 |
| W109 永不生效 | 指标全是形容词也不报 | 数字判定包含章标题，「## 1.」自带数字 |
| W112 漏检 | 用户故事写成陈述句不报 | 要求句中含「作为」才检查 |
| E009 放过空骨架 | 73 分仍判定通过 | 阈值 10 过高，且含 Given 的行被整体跳过 |
| W106 误报 | 「提升额度」「优化器」被判模糊词 | 中文裸子串匹配，无词边界 |

**结论性经验**：门禁的失效几乎从不是"报错了"，而是"永远不报"或"报得太多以至于没人看"。两类都只能靠评测集发现，靠人工读代码发现不了。

## 一份典型的检验报告

```
文档：工作记录便签-PRD-v1.0.md（L2，8 条需求）
第一层  100/100，ERROR 0，WARN 0，退出码 0
第二层  16 项清单通过 15 项，待确认 1 项（Q-004、Q-006 阻塞上线未解决）
第三层  待执行，需研发与测试各一名
第四层  已执行，6 项变异全部检出
结论    可进入评审，但两个阻塞型开放问题未闭环前不得进入开发
```

## 常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 评分 100 就认为需求正确 | 把形式合格当成业务正确 | 100 分只是入场券，第三层才是判据 |
| 用 WARN 数量衡量质量 | 词表覆盖不到的模糊表述被漏掉 | WARN 只看趋势，不看绝对值 |
| 跳过变异测试 | 门禁悄悄失效，之后全是假通过 | 改 lint 规则后必跑 `eval/prd_forge_eval.py` |
| 让作者自己做第三层 | 作者用自己的隐含知识补全空白，看不出问题 | 必须换人 |
| 用默认模式做 CI 卡点 | NFR 未量化、矩阵漏需求这类最常退化项全部放行 | CI 用 `--strict` |
| 误报后直接加豁免词了事 | 豁免越来越多，门禁退化成装饰 | 先确认是不是规则太宽，再考虑 `--allow` |
