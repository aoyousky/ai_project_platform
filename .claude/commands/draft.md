---
description: 从一句话需求生成 Spec Packet 草稿（辅助层，非必经环节）
allowed-tools: Read, Grep, Glob, Write
---

把 `$ARGUMENTS`（一句原话、一段聊天记录、或一份粗糙 PRD）扩写成一份**草稿级** Spec Packet。

## 定位（先读，再动手）

这是**辅助能力，不是流程环节**。产出物是草稿，不是交付依据：

- 草稿写在 `specs/_drafts/`，**不得**写入 `specs/` 根目录
- front-matter 必须含 `status: draft` 与 `generated_from: <原话摘要>`
- 草稿签字前不得用于实现；去掉 `status: draft` 并升版后才是 Spec Packet

若用户要求"直接生成正式 SPEC"，回答：

> 我可以生成草稿，但正式版必须有 PM 与业务方逐条签字的动作。
> 草稿会先落在 `specs/_drafts/`，你确认后 `git mv` 到 `specs/` 并升版即可。

## 追问规则（这条决定草稿质量）

**不要一次问十个问题，也不要一次都不问。**

- 最多 3 轮，每轮 ≤ 5 个问题
- 第 1 轮只问**会让整个方案变形**的问题（角色是谁、影响面多大、有没有存量系统约束）
- 第 2 轮问**会决定断言怎么写**的问题（成功长什么样、失败代价多大、数据从哪来）
- 第 3 轮只补**契约层**空缺（空值、时区、精度、枚举、上限）
- 用户说"你先按常见的来"时，允许先假设，但**必须**在草稿里把假设写成
  `> ⚠️ 待确认假设：<假设内容> —— 若不符请指出，整段需重写`

## 生成结构

按 `specs/SPEC-TEMPLATE.md` 的九段式产出，其中：

1. **元信息**：`status: draft`，`risk_level` 与 `channel` 给出建议值并写明判断理由（影响面 + 是否涉资金/隐私/对外承诺）
2. **断言 A-01…**：5–12 条 P0。Then 必须是四类之一（状态码 / 返回值或 schema / 数值阈值 / 错误码）；前端交互用"元素 + 可见/可用/数量"表述
3. **边界 E-01…**：条数 ≥ 断言数，必须覆盖六类：空值、超限、重复/幂等、权限、超时、非法状态。原文没提到的那几类，用 `> ⚠️ 待确认假设` 标注后给出建议值
4. **数据契约**：字段、类型、可空、空值语义、时区、精度、枚举全量。**空值语义与 0 必须分开写**（`null` 表示未填写，`0` 表示金额为零，二者不可混）
5. **非功能**：性能给数字（P95 + 并发数 + 数据量），脱敏字段点名，留痕要求点名
6. **状态流转**：非法迁移显式写出
7. **Non-goals**：≥ 3 条。**从原话里"没说要做的"反推**，这是最容易漏也最值钱的一段
8. **Golden Samples**：3 正例 + 1 反例。反例要选"看起来合理但违反规格"的行为
9. **变更与签字**：留空，标注"待 PM 与业务方逐条确认"

## 产出后必须做的三件事

1. 跑体检：`bash scripts/spec-audit.sh specs/_drafts/<文件>`
2. 把体检中"Then 不可判定"的条目，在草稿末尾列出**改写前 / 改写后**对照，
   让用户看到抽象要求是怎么变成断言的
3. 输出一张「我做了哪些假设」清单（逐条列出 `⚠️ 待确认假设` 的行号），
   这是用户复核草稿的唯一入口

最后一行固定输出：

```
草稿路径 specs/_drafts/<文件> ｜ 就绪度 <分数> ｜ 待确认假设 <n> 条
下一步：逐条确认假设 → 补签字 → git mv 到 specs/ 并升版
```
